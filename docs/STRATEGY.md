# 차별화 전략 (STRATEGY)

> 작성일: 2026-11-16 · 상태: 팀 논의용 초안
> 관련 문서: `docs/EXPERIMENTS.md`(근거 자료) · `docs/RESEARCH.md`(문제 배경) · `docs/DESIGN.md`(설계)

---

## 0. 요약

- **"동작하는 시스템을 만들었다"는 차별점이 되기 어렵다.** 파이프라인, 비동기 처리, 통신 프로토콜 같은 구현은 다른 팀도 짧은 기간에 비슷한 수준으로 만들 수 있다.
- **차별점은 "이 환경에서 안전하다는 것을 증명했다"에 둔다.** 실물 장비와 시간을 들여야만 얻을 수 있는 검증 결과는 단축하기 어렵다.
- 이를 위한 축은 네 가지다: **① 고장을 보여 주는 시연 ② 측정 근거가 있는 결정 ③ 어려운 문제 하나를 정면으로 다루기 ④ 한계의 공개.**

---

## 1. 현황 인식

### 1.1 빠르게 끝난 것과 오래 걸린 것

| 빠르게 끝난 것 | 실물과 시간이 필요했던 것 |
|---|---|
| 파이프라인 구조, 스레드, 모듈 추상화 | 손으로 렌즈를 가렸더니 **Y가 출력됨** (E-01) |
| ESP32 통신 프로토콜, 펌웨어 | 웹캠 노이즈가 0.20이라 임계값 0.5가 틀림 (E-02) |
| 테스트 코드, 가상 시나리오 | 보드에 사용자 LED가 없음 (EXP-006) |
| 문서, 다이어그램 | RPi에서 640 모델은 FAULT만 반복, 방열 없이 79 °C 도달 (E-08, E-09) |

왼쪽은 구현이고, 오른쪽은 **검증**이다. 오른쪽 항목은 모두 설계 단계에서는 예상하지 못했고, 실제 장비로 실험한 뒤에야 드러났다.

### 1.2 판단

"그럴듯하게 동작하는 시스템"과 "실제 환경에서 검증된 시스템" 사이의 간격에서 시간이 들고, 그 간격에서 팀 간 차이가 난다. 차별화의 무게는 이 간격에 둔다.

## 2. 차별화 축

### ① 고장을 보여 주는 시연

일반적인 시연은 정상 흐름(사람 진입 → N, 퇴장 → Y)을 보여 준다. 안전 시스템의 설득력은 **고장 상황에서도 N이 된다는 것**을 직접 보여 줄 때 생긴다.

| 시연 항목 | 기대 결과 | 현재 상태 | 근거 |
|---|---|---|---|
| USB 케이블 분리 | 0.5초 안에 N, 재연결 시 복구 | **실기 검증 완료** | EXP-006 |
| RPi 프로그램 강제 종료 | ESP32 워치독으로 N | 송신 중단 실기 검증 완료 (501 ms) | EXP-006 |
| 프로그램 정상 종료 | 마지막 송신 N | **실기 검증 완료** | EXP-006 |
| 검증 중 사람 재진입 | 즉시 N, 타이머 초기화 | 가상 시나리오 통과, 실기 미검증 | S2 |
| 카메라 화면 정지 | FAULT → N | 가상 시나리오 통과, 실기 미검증 | S9, E-02 |
| **렌즈 가림** | FAULT → N | **미해결 (현재 Y가 나옴)** | E-01 |
| 깨진 통신 패킷 | 무시, N 유지 | 실기 검증 완료 | EXP-006 |

렌즈 가림(E-01)을 해결하면, 고장 시연 목록 전체를 실기로 보여 줄 수 있다.

### ② 측정 근거가 있는 결정

설계 결정마다 측정값을 근거로 제시한다.

| 결정 | 근거 |
|---|---|
| 모델 입력 320 사용 (640 미사용) | RPi에서 640은 추론 424 ms(단독) / 840 ms(파이프라인)로 프레임 유효 기간 500 ms를 넘어 FAULT가 반복된다 (EXP-005) |
| 추론 3스레드, 카메라 15 fps | 4스레드·30 fps는 CPU 경합으로 시작 직후 FAULT 발생, 3스레드·15 fps는 FAULT 없음 (EXP-005) |
| ESP32 워치독 500 ms | 하트비트 200 ms 기준 **연속 1개 손실까지** 허용 (2개 연속 손실이면 다음 패킷이 600 ms라 500 ms에 N), 실측 501 ms에 N (EXP-006, E-13) |
| 화면 정지 판정 0.05 / 15프레임 | 웹캠 정지 장면 노이즈 0.20~0.28 실측 (EXP-001) |
| 방열 대책 필요 | 연속 추론 시 79 °C, 소프트 온도 제한 발생 (EXP-005) |

`docs/EXPERIMENTS.md`가 이 근거들의 기록이다. 실험할 때마다 이 문서를 갱신한다.

### ③ 어려운 문제 하나를 정면으로 다루기

**차 안에 남은 사람(E-03)** 은 대표 사망사고의 직접 원인이다 (`docs/RESEARCH.md` §1.2). 위에서 내려다보는 카메라로는 원리상 보이지 않는다.

- 이 한계를 숨기지 않고 **먼저 보여 준다.** 카메라만으로는 실패하는 장면을 시연한다.
- 이어서 원리가 다른 센서(레이더, 열화상 등)를 더해 해결하는 흐름을 보여 준다. 원리가 다른 센서는 같은 이유로 동시에 실패할 가능성이 낮다.
- 구조 변경은 작다. 새 센서를 `Detector` 하나로 추가하고, 판단은 "어느 한쪽이라도 사람을 감지하면 N"으로 합친다.
- 현재 카메라 후보에 열화상이 포함되어 있으므로, 카메라 선정과 함께 논의한다.

### ④ 한계의 공개

"되는 것 / 안 되는 것 / 안 되는 것을 어떻게 막았는가"를 표 한 장으로 제시한다. `docs/EXPERIMENTS.md` §1 엣지 케이스 목록을 그대로 쓴다.

- 심사나 질의응답에서 "이런 상황이면 어떻게 되는가"라는 질문에 **이미 실험했다**고 답할 수 있다.
- 미해결 항목도 원인과 다음 계획을 함께 적는다.

## 3. 설계 역량의 위치

설계 역량의 가치는 구조도 자체가 아니라 **트레이드오프 판단**에 있다.

| 구조 (쉽게 떠올릴 수 있음) | 트레이드오프 판단 (설명할 수 있어야 함) |
|---|---|
| 스레드 3개로 분리 | 왜 일반 큐가 아니라 최신 1장만 유지하는가 (지연 누적 방지) |
| Y/N 상태 기계 | 왜 Y는 3초 **그리고** 10장인가 (낮은 fps에서 시간 조건만으로는 2~3장만 보고 통과) |
| ESP32 연결 | 왜 워치독을 RPi가 아니라 ESP32에 두는가 (RPi가 멈춰도 안전) |
| 센서 여러 개 | 판단을 AND로 합치면 놓침은 줄고 불필요한 N은 늘어난다 |

## 4. 팀 운영 원칙

### 4.1 각자 모듈을 직접 구현한다
- 공유 대상은 인터페이스(`core/packets.py`, 각 `*_api.py`)와 문서다.
- 기존 구현은 정답지가 아니라 **"무엇을 검증해야 하는지 보여 주는 지도"** 로 쓴다. 앞서 있는 것은 코드가 아니라 **어디서 실패하는지 알고 있다는 점**이다.
- 각자 모듈을 만들면서 실패를 직접 겪고, 그 결과를 EXPERIMENTS에 기록한다.

### 4.2 모든 팀원이 답할 수 있어야 하는 질문

| 예상 질문 | 답의 근거 |
|---|---|
| 왜 Y가 나오기까지 3초가 걸리는가? | 비대칭 판단 원칙 (DESIGN §2, §8) |
| 카메라가 멈추거나 가려지면 어떻게 아는가? | 카메라 상태 검사 (DESIGN §3.5), E-01·E-02 |
| RPi가 멈추면 어떻게 되는가? | ESP32 워치독 500 ms (DESIGN §7.3, EXP-006) |
| AI가 틀리면 사고가 나지 않는가? | 기존 안전장치를 대체하지 않고 **막는 권한만** 가진 보호층 (RESEARCH §3.2) |
| 왜 더 큰 모델(640)을 쓰지 않는가? | RPi 실측 (EXP-005) |
| 차 안에 사람이 있으면? | 현재 한계 (E-03), 해결 방안 (§2-③) |
| 쓸데없이 N이 자주 나오면? | 가용성 문제로 별도 관리 (E-02, E-08) |
| 다른 현장에도 쓸 수 있는가? | ROI만 바꾸면 위험구역 판정기로 일반화 가능 (RESEARCH §5) |

## 5. 실행 우선순위 (제안)

| 순위 | 작업 | 차별화 축 |
|---|---|---|
| 1 | 렌즈 가림(E-01) 해결 → 고장 시연 목록 완성 | ① |
| 2 | 실제 시연 환경(모형)에서 놓침률·불필요 N 비율·카메라→ESP32 지연 측정 | ② |
| 3 | 차 안 사람(E-03) 대응 센서 결정 및 실험 | ③ |
| 4 | 엣지 케이스 표와 예상 질문 답변을 발표 자료로 정리 | ④ |

---

## 6. 팀 논의 안건

1. **평가 기준 확인:** 기술 완성도, 문제 정의, 시연, 확장성 중 비중이 큰 항목에 따라 §2의 힘 배분을 조정한다.
2. **차 안 사람(E-03)에 도전할지:** 센서 종류(레이더 / 열화상), 예산, 배송 기간.
3. **시연 시나리오 확정:** §2-① 표에서 실제로 보여 줄 항목.
4. **역할 분담:** 모듈별 담당과, 각 담당자가 맡을 실험(EXPERIMENTS) 항목.
