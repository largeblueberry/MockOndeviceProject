# 엣지 케이스 · 실험 기록 (EXPERIMENTS)

> 본 문서는 시스템이 실패할 수 있는 상황(엣지 케이스)과 실제 장비로 수행한 실험의 결과를 기록한다.
> 관련 문서: `docs/DESIGN.md` §3.5(장애 감지), §6.2(시나리오 목록) · `docs/PROGRESS.md`(진행 현황)

---

## 0. 작성 규칙

- 엣지 케이스는 `E-번호`, 실험은 `EXP-번호`로 식별한다. 번호는 재사용하지 않는다.
- 위험은 두 종류로 구분한다.
  - **안전:** 사람이 있는데 Y가 나올 수 있는 경우. 최우선으로 처리한다.
  - **가용성:** 사람이 없는데 N이 계속되는 경우. 안전하지만 시스템이 쓸모없어진다.
- 실험 결과는 장비, 설정값, 측정값을 함께 기록한다. 임계값은 카메라마다 다르므로 측정 조건 없이 수치만 남기지 않는다.

### 1.2 해결 (가상 시나리오로 검증)

`scenarios/`의 9개 시나리오는 sync / threaded 두 모드 모두 통과하며, 모든 시나리오에서 "실제로 사람이 있는데 Y"는 0회다.

| ID | 시나리오 | 상황 | 기대 결과 |
|---|---|---|---|
| S1 | `entry_normal` | 정상 입차: 하차 → 퇴장 | 퇴장 후 `clear_time_s` 뒤 Y |
| S2 | `reenter` | 검증 중 재진입 | 재진입 즉시 N, 타이머 초기화 |
| S3 | `flicker` | 검출 깜빡임 (miss_rate 30%) | 사람이 있는 동안 Y 없음 |
| S4 | `camera_outage` | 프레임 2초 끊김 | FAULT(N), 복구 후 재검증 |
| S5 | `stale_frames` | 추론 700 ms (> 500 ms) | 항상 N |
| S6 | `exit_normal` | 정상 출차 | 구역이 비면 `clear_time_s` 뒤 Y |
| S7 | `roi_boundary` | ROI 밖 사람 / 경계에 걸친 사람 | 밖은 Y, 걸치면 N |
| S8 | `camera_blackout` | 완전 암전 중 사람 진입 | 밝기 이상 → N |
| S9 | `camera_freeze` | 화면 정지 중 사람 진입 | 정지 감지 → N |

> S8은 **완전 암전**만 다룬다. E-01(빛이 새는 반암전 + 노이즈)은 아직 시나리오가 없다.

### 1.3 코드 리뷰로 찾은 경우 (2026-11-17, EXP-008)

외부 AI 코드 리뷰(커밋 `059f914` 기준)에서 지적된 항목 중, 코드에서 직접 확인한 것이다. 실제 장비 실험이 아니라 **코드 경로 분석 + 단위 테스트 재현**으로 찾았다.

| ID | 상황 | 위험 | 원인 | 상태 |
|---|---|---|---|---|
| **E-10** | worker가 멈추면, 이미 낸 Y가 **근거 영상보다 오래** 송신됨 (근거 프레임 기준 최악 약 1.3초) | **안전** | 하트비트가 판단 시각(`decided_at`)만 검사하고 촬영 시각은 보지 않음. 재송신해도 SEQ가 증가해 ESP32 워치독도 정상으로 봄 | **해결**: Y는 근거 프레임 나이도 검사 (`runners.py` `expire_decision`). 최악 약 0.8초 (600 ms + 하트비트 주기) |
| **E-11** | worker가 1~2초 밀렸다가 돌아오면, 최신 프레임 1장으로 **재검증 없이 Y** 복귀 | **안전** | `LatestSlot`이 항상 최신 프레임을 주므로 `stale_frame`·`no_frame`에 안 걸림. FSM은 자기가 못 본 공백을 모름. 공백 동안 들어와 가려진 사람을 놓칠 수 있음 | **해결**: 직전 처리 프레임과 간격이 `max_frame_age_ms` 초과면 `frame_gap` FAULT → 복구 → 처음부터 재검증 (`fsm.py` `_input_fault`) |
| E-12 | 카메라 이상(암전·정지)을 알아도 **추론이 끝날 때까지** N이 늦어짐 (RPi 100~250 ms) | 안전 (지연) | `process_frame`이 health 결과와 상관없이 `predict()`를 먼저 실행 | **해결**: health 이상이면 추론을 건너뛰고 바로 N (`runners.py` `process_frame`) |
| E-13 | 문서에 "워치독은 패킷 **2개** 손실까지 허용"이라고 잘못 적힘 | 문서 | 200·400 ms 패킷이 연속 손실되면 다음 패킷(600 ms) 전에 500 ms에 타임아웃. 실제로는 **연속 1개**까지 | **해결**: `STRATEGY.md` 수정. 동작은 안전 방향이라 코드 변경 없음 |
| E-14 | 시나리오 검사가 "근거 프레임 시각에 사람이 있었나"만 봄. 하트비트가 재송신한 Y는 검사하지 않음 → E-10 같은 경우를 못 잡음 | 검증 공백 | `scenario_check.py` `unsafe_yes()`가 worker 판단만, 근거 프레임 시각 기준으로 검사 | 미조치 (다음 작업: 송신된 Y의 시간 구간과 실제 사람 구간이 겹치는지 검사) |
| E-15 | 웹캠 `timestamp`가 촬영 시각이 아니라 `read()` 반환 시각 | 안전 (작음) | 카메라 버퍼에 프레임이 밀려 있으면 실제보다 최근 시각으로 기록 → 프레임 나이가 짧게 계산됨 | 미조치 (지연 크기 실측 필요, EXP-004에서 함께) |
| E-16 | 화면 대비(contrast)를 계산하지만 판정에 쓰지 않음 | 안전 | `health.py`가 `last_contrast`를 로그용으로만 사용 | 미조치 = E-01과 같은 작업 (EXP-002) |

> "사람이 있는데 Y = 0회"(§1.2)는 **근거 프레임 시각 기준**의 결과다. E-14를 해결하기 전까지는 송신·ESP32 출력 기준으로는 확인하지 않았다.

## 2. 실험 기록

### EXP-001 · PC 웹캠 + YOLO 실시간 동작 (2026-11-14)

**환경**

| 항목 | 값 |
|---|---|
| 장비 | PC 내장/USB 웹캠, CPU 추론 |
| 설정 | `config/webcam_yolo.yaml` |
| 모델 | yolo11n, 입력 320 (ONNX Runtime) |
| 카메라 | 640x480 @ 30 fps |

**성능**

| 항목 | 결과 |
|---|---|
| 처리량 | 캡처 30 / 모델 30 fps (버린 프레임 0) |
| 추론 시간 | 평균 8.1~8.8 ms |
| 하트비트 | 200 ms 주기, 지연 0회 |
| 사람 검출 | 화면 진입 약 1초 내 OCCUPIED. 얼굴을 지갑으로 가려도 OCCUPIED 유지 |
| 퇴장 → Y | 빈 화면 약 3초 후 `[Y] CLEAR` |

**카메라 측정값 (프레임 차이 diff)**

| 장면 | diff |
|---|---|
| 가만히 앉아 있음 | 0.25 ~ 0.28 |
| 빈 배경 | 0.20 ~ 0.25 |
| 움직임 | 최대 ~58 |
| 렌즈 손으로 가림 | 0.95 ~ 9 (fps 30 → 20으로 하락) |

**발견 사항**
- E-02 발견 → `freeze_diff_threshold` 0.5 → **0.05**, `freeze_frames` 1 → **15**(30 fps 기준 약 0.5초)로 조정 (`config/webcam_yolo.yaml`).
- E-01 발견 (21:18:24~33 구간) → 미조치. 원인 분석용으로 지표 로그에 밝기(bright)·대비(contrast) 범위 출력을 추가했다.

**결론**
1. 가상 데이터로 만든 구조가 설정 파일 교체만으로 실제 웹캠·실제 모델에서 동작했다.
2. PC 기준 추론 8 ms로, 성능은 현 단계의 병목이 아니다.
3. 발견된 문제는 모두 모델이 아니라 **카메라 상태 판단**에서 나왔다. 핵심 과제는 "사람 검출"보다 "검출할 수 없는 상황을 알아채는 것"이다.
4. 임계값은 카메라마다 측정해야 한다. 카메라가 바뀌면(RPi) 다시 측정한다.

### EXP-006 · ESP32 펌웨어 실기 검증 (2026-11-16)

**환경**

| 항목 | 값 |
|---|---|
| 장비 | 노트북(Windows) + ESP32 DevKit (USB-UART CP210x, COM7) |
| 펌웨어 | `firmware/esp32/psafe_gate` (PlatformIO `esp32dev`, Arduino 프레임워크). RAM 6.6%, Flash 20.6% |
| 프로토콜 | v1 (DESIGN §7.3), 115200 bps |
| 출력 | 내장 LED (GPIO 2, 켜짐 = Y) |

**결과 1: `mcucheck` 자동 점검 — 7/7 통과**

| # | 항목 | 결과 |
|---|---|---|
| 1 | N 패킷 → N 유지 | 통과 |
| 2 | Y 패킷 → Y 전환 | 통과 (0.02초) |
| 3 | 송신 중단 → 워치독 N | 통과. ESP32 기준 마지막 유효 패킷 후 **501 ms**, PC 기준 마지막 송신 후 0.53초 |
| 4 | CRC 오류 Y → 무시 | 통과 (`bad_crc` 5건, N 유지) |
| 5 | 같은 SEQ 반복 → 무시 | 통과 (`dup` 집계, 반복 시작 0.30초 후 워치독 N) |
| 6 | FAULT인데 Y → 무시 | 통과 (`invalid` 5건, N 유지) |
| 7 | Y 중 N 패킷 → 즉시 N | 통과 (0.05초) |

포트를 열 때 ESP32가 리셋되며(부팅 ROM 메시지 후 `BOOT N`), 부팅 직후 N 상태를 확인했다.

**결과 2: 파이프라인 연결** (`config/serial_dummy.yaml`, 가상 시나리오 반복, 32초)
- 콘솔 판단 순서: INIT → VERIFYING → **Y**(3초) → OCCUPIED → VERIFYING → **Y**(12초) → … → 종료 시 FAULT(`shutdown`)
- 시리얼 송신 161 패킷, 오류 0. 하트비트 160회, 오래된 판단 0회
- LED 표시와 콘솔 판단의 일치는 육안 확인 필요

**남은 확인**
- [x] 판단과 ESP32 출력 일치 — **통과 (로그로 확인).** 보드의 빨간 LED는 전원 LED로 추정되며 GPIO 2 사용자 LED가 없어 육안 확인은 불가. 대신 `serial_out`이 ESP32 상태 줄을 읽어 로그로 남기도록 했다 (결과 3)
- [x] 종료 시 N — **통과 (로그로 확인).** 종료 경로는 Ctrl+C와 같다 (결과 3)
- [x] 실행 중 USB 분리 → 재연결 시 송신 재개 — **통과** (11:10:54 쓰기 실패 `PermissionError(13)` → 11:10:57 `reconnected`, 재연결 1회, 오류 1건. 분리 중 판단은 계속 진행되었고 ESP32는 워치독으로 N 상태)

**결과 3: 판단과 ESP32 관문 상태 대조** (`serial_out`이 ESP32 상태 줄을 로그로 기록, 20초)

| 시각 | 파이프라인 판단 | ESP32 보고 |
|---|---|---|
| 11:17:18 | INIT → VERIFYING (N) | `BOOT N` |
| 11:17:21 | **Y** CLEAR | `GATE Y seq=16` |
| 11:17:23 | N OCCUPIED | `GATE N reason=packet_n` |
| 11:17:30 | **Y** CLEAR | `GATE Y seq=60` |
| 11:17:38 | N FAULT (`shutdown`) | `GATE N reason=packet_n` → 종료 시 관문 N |

- 판단이 바뀐 4번 모두 같은 초 안에 ESP32가 같은 상태를 보고했다. 불일치 0건, 송신 102 패킷, 오류 0
- VERIFYING처럼 판단은 바뀌어도 Y/N이 그대로인 전환에서는 ESP32 보고가 없다 (관문은 Y/N만 본다). 정상이다

**결론**
- 펌웨어와 RPi 쪽 인코딩이 프로토콜 v1로 일치한다. 가상 ESP32(`protocol.Receiver`)와 실기의 동작이 같았다.
- 워치독은 설계값(500 ms)대로 동작한다. RPi가 멈추거나 케이블이 빠져도 약 0.5초 안에 N이 된다.

### EXP-007 · RPi 환경 구성 및 Mock 연결 검증 (2026-11-16)

**환경**

| 항목 | 값 |
|---|---|
| 보드 | Raspberry Pi 4 Model B Rev 1.5, 메모리 4 GB, 방열판·팬 없음 |
| OS | Debian 13 (trixie), 커널 6.18, aarch64 |
| Python | 3.13.5 (venv) |
| 패키지 | numpy 2.5.5, **opencv-python-headless** 5.0.0, onnxruntime 1.32.0 (CPU), pyserial 3.5 |
| 접속 | 노트북에서 SSH 키 인증 (`linux@192.168.20.22`), 저장소는 `git clone` |

**설치 중 발견**
- `opencv-python`은 `libGL.so.1`이 없어 import 실패. RPi에는 화면이 없으므로 같은 버전의 `opencv-python-headless`로 교체했다 (sudo 불필요). 화면 표시(`viewer` Output)는 RPi에서 쓰지 않는다.

**결과**

| 항목 | 결과 |
|---|---|
| 단위·통합 테스트 | 100개 통과 (실제 YOLO 모델 테스트 포함) |
| 실시간 스레드 테스트 (`-m slow`) | 9개 통과 (1분 55초) |

- 640과 320은 같은 모델(yolo11n, 파일 10.6 / 10.7 MB)이고 **입력 픽셀 수만 4배**다. 추론 시간도 약 4배(424 / 105 ms)다.
- 온도는 **사용 코어 수 × 지속 시간**에 따라 오른다. 같은 320에서 1스레드 52.5 °C, 4스레드 63.3 °C. 640·4스레드는 47초 동안 4코어를 채워 74.5 °C.
- 결과 3의 79 °C는 벤치마크와 파이프라인 실험을 휴식 없이 이어 하고, 파이프라인에서는 가상 카메라 프레임 생성까지 CPU를 쓴 결과다.
- 실제 운용은 연속 동작이므로, 순간 최고치보다 **장시간 정상상태 온도**를 측정해야 한다 (E-09).

**결론**
1. **RPi 기본 구성은 320 모델, 추론 3스레드, 카메라 15 fps로 한다.** 모델 6.6 fps에서 10장은 약 1.5초라, Y까지 시간은 `clear_time_s`(3초)가 결정한다.
2. 640은 현재 설정으로 사용 불가. 쓰려면 유효 기간을 늘려야 하는데, 이는 오래된 정보로 판단하는 것이므로 안전과 맞바꾸는 결정이다. 가속(NCNN 등, DESIGN §14) 측정이 먼저다.
3. 장시간 운용에는 방열판·팬이 필요하다 (E-09).
4. 처리 지연이 크면 `stale_frame` FAULT로 N이 길어진다 (E-08). 안전에는 문제가 없지만 가용성 문제다.

### EXP-008 · 외부 코드 리뷰 검증 및 반영 (2026-11-17)

**방법** 외부 AI 코드 리뷰(Codex·Gemini, 커밋 `059f914` 기준)의 지적을 코드에서 줄 단위로 확인했다. 맞는 지적 중 작게 고칠 수 있는 것을 먼저 수정하고, 각 경우를 재현하는 테스트를 추가했다. 실제 장비 실험은 하지 않았다.

**찾은 경우와 조치** §1.3의 E-10~E-16

| ID | 수정 전 (재현 테스트) | 수정 후 | 테스트 |
|---|---|---|---|
| E-10 | 0 ms에 찍은 프레임으로 490 ms에 만든 Y가 1,080 ms에도 송신됨 | 근거 프레임 나이 > 600 ms면 `decision_stale` N | `test_runner_logic.py::test_y_expires_by_evidence_age_not_only_decision_age` |

**가용성 확인** `frame_gap` 임계값은 `max_frame_age_ms`(500 ms)를 그대로 쓴다. RPi 기본 구성의 처리 간격은 약 150 ms(EXP-005, 모델 6.6 fps)라 정상 운용에서는 걸리지 않는다. 0.4초 간격은 FAULT가 아님을 테스트로 확인했다 (`test_small_frame_gap_is_not_fault`). E-10의 근거 프레임 나이도 RPi 기본 구성에서 최대 약 0.4초로 추정되어 600 ms에 걸리지 않는다.

**결과** 단위 테스트 107개, 실시간 테스트 9개, 시나리오 9개(sync·threaded) 모두 통과.

**리뷰 중 보류한 지적**
- 낮은 신뢰도(< 0.30) 검출을 "판별불가"로 처리: 사실상 임계값을 낮추는 것과 같아 오감지로 인한 불필요한 N이 늘어난다. 시연 환경에서 측정한 뒤 결정한다.
- 미래 시각·NaN 타임스탬프 거부, 설정값 범위 검증: 현재 Source에서는 생기지 않는다. NaN은 Y가 나오지 않는 방향이다. 새 센서를 붙일 때 함께 처리한다.
- 다중 센서 합성 계층(PermitCoordinator), 입차 건 단위 검사: 원칙("위험은 OR, 허가는 AND", 필수 센서는 설정 목록으로)은 채택한다. 구현은 보조 센서 종류가 정해진 뒤에 한다. `RESEARCH.md` §4.1의 "Detector 하나만 추가하면 된다"는 현재 단일 Source·Detector 구조에서는 맞지 않는다.

### EXP-009 · 다중 보드 통신: PC 한 대에서 A·B·C 프로세스 3개 (2026-11-19)

| 절차 | `config/webcam_yolo.yaml`로 실행하고 ① 가만히 10초 ② 빈 배경 10초 ③ 렌즈 손으로 가림 10초. 지표 로그(5초 주기)의 bright / contrast / diff 범위를 구간별로 기록 |
| 기대 | 가림 구간의 contrast가 정상 구간보다 확연히 낮다 |
| 후속 작업 | `safety/health.py`에 `low_contrast` 검사 추가, `camera_covered` 시나리오와 테스트 추가 |
| 통과 기준 | 렌즈 가림 10초 동안 Y 0회, 정상 장면에서 `low_contrast` 오탐 0회 |

### EXP-003 · 화면 정지 임계값 재확인 (E-02)

| 항목 | 내용 |
|---|---|
| 목적 | 조정한 값(0.05 / 15프레임)이 정지 장면 오탐을 없앴는지 확인한다 |
| 절차 | 가만히 있는 장면, 빈 배경을 각각 30초 이상 유지 |
